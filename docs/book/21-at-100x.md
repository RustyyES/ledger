# Chapter 21 — At 100x

500 million orders. 50 million customers. What stops working, roughly in the
order it breaks.

This is the question a senior interviewer asks, and the reason they ask it is
that the answer reveals whether you understand *why* your design works, or just
*that* it does.

---

## 1. DuckDB — the first hard wall

**Breaks at:** ~50–100M rows on one machine, sooner with concurrency.

A single-file embedded engine on one box has no horizontal scaling. The dbt
project already targets Snowflake via `--target prod`, and the SQL is written to
compile on both — which is why `days_in_month` and `raw_source` are macros rather
than inline dialect-specific SQL.

**What changes beyond the connection string:**

- `dim_customer` needs clustering on `(customer_id, valid_from)` — the as-of
  range join is the hottest query in the warehouse.
- Facts need partitioning on `order_date`.
- `delete+insert` needs to become `insert_overwrite` (see §3).

**Why not just a bigger machine?** You can get to maybe 500M rows on a large
instance. You cannot get to concurrent readers, and the metrics API plus the
dashboard plus analysts are all readers.

---

## 2. The sink becomes the bottleneck before the warehouse does

**Breaks at:** roughly 40–60k records/second for one Python consumer.

At 100x the write volume that isn't enough. In the order I'd actually try:

**a. One consumer group per table.** The schema guard already isolates tables, so
this is a deployment change rather than a redesign. Buys ~7x. Cheapest win by a
wide margin.

**b. Move the Parquet write off the consumer thread** into a bounded writer pool.
The consumer becomes I/O-bound on Kafka rather than CPU-bound on compression.

**c. Only then** consider Flink or Spark Structured Streaming — and accept
**losing the explicit control over commit ordering** that Chapter 8's guarantee
depends on. Those frameworks have their own checkpointing semantics, and they're
good, but they're not *yours*.

> Note the ordering. Two deployment changes before a rewrite. The instinct to
> reach for a streaming framework first is usually the expensive wrong answer.

---

## 3. `delete+insert` becomes ruinous

**Breaks at:** roughly 100M rows in a fact table.

Rewriting a 21-day window of a 500M-row table on every run is hours of work to
update a few thousand rows.

**The answer:** real partitioning. `insert_overwrite` on date partitions, so only
*touched* partitions are rewritten.

That requires the warehouse to support partition-level replacement — which is a
concrete, specific reason to leave DuckDB, not a vague "it'll be faster".

---

## 4. The lookback becomes the wrong mechanism

**Breaks at:** the point where the window is enormous relative to what changed.

A 21-day reprocessing window over 500M rows re-derives tens of millions of rows
to correct a few thousand.

**The right shape:** a **change-log-driven** rebuild. The sink already knows
exactly which `payment_id`s were touched in each batch — it just doesn't tell
anyone. Have it emit that set, and the incremental model reprocesses precisely
those rows.

> The lookback is a *proxy* for "what changed". It's correct and cheap at this
> scale, and correct and ruinous at 100x. Knowing that a design is a proxy — and
> what it's a proxy *for* — is what lets you replace it cleanly.

---

## 5. In-memory sorting stops fitting

`_dedupe_by_offset` and the pre-write sort are O(batch) in memory.

At larger batch sizes this needs an external merge sort, or smaller batches and
more files — which then needs **compaction**, which is an entire subsystem this
project doesn't have.

This is a good moment to reconsider Iceberg (Chapter 20), which gives you
compaction and transactional partition replacement as table features rather than
as code you maintain.

---

## 6. One Postgres, one slot, one publication

**Breaks at:** high write volume, and it breaks *operationally* rather than
computationally.

At 100x the write rate, WAL retention on the replication slot becomes a genuine
risk. `max_slot_wal_keep_size = 4GB` starts actually firing, which kills the slot
— which means re-snapshotting.

The heartbeat (Chapter 7) mitigates the *idle* case. It does nothing for the
*volume* case.

**Where that points:** multiple publications by table group, so a slow consumer
on one group doesn't retain WAL for all of them. Eventually, sharding the source
— at which point CDC becomes N pipelines and the ordering guarantees get
genuinely harder.

---

## 7. Testing against a fixture stops being enough

The CI fixture is 0.4% scale. It keeps all six messiness patterns — which is what
makes it useful — but it **cannot catch a query plan that degrades at volume**.

A model that's fine on 20k rows and does a nested loop join on 500M is invisible
in CI.

**What's needed:** a scheduled large-scale run against a production-sized clone.
A nightly job, not a PR gate — because a PR gate that takes two hours is a PR
gate people learn to bypass.

---

## 8. Secrets

`infra/debezium/secrets.properties` is committed with development credentials.

At any real scale that file is rendered at deploy time from a secret manager and
never exists in git. The `${file:...}` indirection is **already in place**
precisely so that swap is a deployment change rather than a code change.

That's worth noting as a pattern: when you take a shortcut, take it in a way that
makes the real solution a configuration change.

---

## 9. One Airflow, `LocalExecutor`

**Breaks at:** more DAGs than one machine's worth of parallelism.

`LocalExecutor` runs tasks as subprocesses on the scheduler host. That's right
for three DAGs and wrong for three hundred.

**The path:** `CeleryExecutor` (a worker pool) or `KubernetesExecutor` (a pod per
task). Kubernetes gives per-task resource isolation, which matters when one dbt
run can eat all the memory.

---

## What does *not* break

Worth stating, because it's the interesting half of the answer:

**The layer contract.** staging → intermediate → marts scales fine. The
discipline gets *more* valuable as models multiply.

**The reconciliation tests.** They compare aggregates, so they cost the same
relative to data size. They get *more* valuable — more places for a subtle bug to
hide.

**The `_ingested_at` concept.** The *mechanism* changes (§4), the *idea* — filter
on arrival time, not event time — is scale-independent and correct.

**SCD2.** The volume grows and the shape is unchanged. Just needs clustering.

**Write-then-commit.** Correct at any scale. Two lines, permanently right.

**Idempotency.** More important at scale, not less.

> **The architecture survives; the implementations get replaced.** That's the
> mark of a design where the boundaries are in the right places — you can swap
> what's inside a box without redrawing the boxes.

---

## The honest summary

At 100x you would keep:

- the layer contract and the modelling approach
- every test, especially the reconciliation ones
- the incremental *concept*
- the schema guard's policy (though probably not its implementation)

You would replace:

- DuckDB → Snowflake / BigQuery / Iceberg
- `delete+insert` → `insert_overwrite` on partitions
- the lookback → a change-log-driven rebuild
- one sink → a consumer group per table, then possibly a streaming framework
- `LocalExecutor` → Celery or Kubernetes
- committed dev credentials → a secret manager

That's a reasonable ratio. If the answer were "replace everything", the design
was wrong. If it were "change nothing", you haven't thought about it.

---

## The last word

If you take one thing from this book, take this:

> **The hard part of data engineering is not moving data. It's knowing whether
> the number at the end is right — and building a system that tells you when it
> isn't.**

Everything here — the reconciliation tests, the byte-identical replay, the schema
guard, the lookback, the provenance flags, the freshness 503 — exists to serve
that one goal.

Ten bugs. Zero exceptions. That's the job.
