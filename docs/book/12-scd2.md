# Chapter 12 — Slowly changing dimensions, or the time-travel problem

> Source: [`transform/snapshots/customer_snapshot.sql`](../../transform/snapshots/customer_snapshot.sql),
> [`models/marts/core/dim_customer.sql`](../../transform/models/marts/core/dim_customer.sql)

## The scenario

A customer signs up in Cairo in March 2025. Over eighteen months they place 40
orders. In June 2026 they move to Berlin and update their profile.

The source table now says:

```
customer_id | country_code | updated_at
abc-123     | DE           | 2026-06-14
```

Egypt is gone. Overwritten. Postgres kept no history — it wasn't asked to.

Now run this report:

```sql
select customer_country, sum(amount) from orders group by 1
```

Every order that customer ever placed is now attributed to **Germany** —
including the 38 placed while they lived in Egypt.

## Why this is worse than it sounds

Run that report in May 2026 and again in July 2026, for the *same historical
period*, and you get **different numbers**.

- No code changed.
- No data was corrected.
- No bug was introduced.
- The numbers just moved.

Someone will notice, ask why, and you won't be able to explain it — because from
inside the warehouse there's nothing to see. The old value doesn't exist
anywhere.

> This is called **retroactive restatement**, and it destroys trust faster than
> being wrong once. Being wrong once is a bug. Being *unstably* right means
> nobody can rely on any number you produce.

## The three responses

The classic taxonomy. Worth knowing the names.

**Type 0 — never update.** The dimension records what was true at first sight.
Fine for immutable attributes (birth date). Wrong here — you genuinely need to
know where they live now.

**Type 1 — overwrite.** The dimension always shows current state. Simple. It is
what causes the problem above. Correct when history genuinely doesn't matter —
`dim_plan` is Type 1 for this reason.

**Type 2 — keep every version, with validity windows.** More rows, more
complexity, and it's the only one that answers "what was true then?"

## What Type 2 looks like

Instead of one row per customer, one row per customer **per version**:

```
customer_key  customer_id  country  valid_from   valid_to     is_current
aaa111        abc-123      EG       2025-03-01   2026-06-14   false
bbb222        abc-123      DE       2026-06-14   NULL         true
```

The customer has two rows. Each covers a time window. `valid_to = NULL` means
"still true".

Now the query from Chapter 11 works:

```sql
left join dim_customer d
    on  d.customer_id = o.customer_id
    and o.placed_at_utc >= d.valid_from
    and o.placed_at_utc <  d.valid_to_or_infinity
```

An order from April 2025 matches the *first* row and gets Egypt. An order from
July 2026 matches the second and gets Germany. Both correct, permanently.

## How dbt does it

A **snapshot** — a special model type that runs periodically and records
changes:

```sql
{% snapshot customer_snapshot %}
{{ config(
    target_schema='snapshots',
    unique_key='customer_id',
    strategy='timestamp',
    updated_at='updated_at',
    invalidate_hard_deletes=True
) }}
select customer_id, email, customer_name, country_code, ...
from {{ ref('stg_customers') }}
{% endsnapshot %}
```

Each run, dbt compares current state against what it has. If `updated_at` moved,
it closes the old row (`dbt_valid_to = now`) and inserts a new one.

**Snapshots are one of the few genuinely stateful things in dbt.** You cannot
rebuild history by re-running them. If you don't snapshot on Tuesday, Tuesday's
state is gone forever. That has a real operational consequence — it's why
`transform_dag` runs the snapshot *before* the models, and why a failed snapshot
is a bigger deal than a failed model.

## `timestamp` vs `check`, and the assumption underneath

Two strategies:

**`check`** — compare a list of columns every run. Use when the source has no
reliable modification timestamp. Costs a full-table comparison each run, and
cannot see a change that was reverted between two runs.

**`timestamp`** — trust `updated_at`. Cheap. But it relies on the application
touching `updated_at` on **every** mutation.

That's an assumption about code you don't own, and it is load-bearing. A route
that forgets to touch it produces a version that is **never recorded** —
silently.

Which is why this test exists on the *other* side of the boundary:

```python
def test_patch_moves_updated_at(client, customer):
    """The dbt snapshot's timestamp strategy depends on this without exception."""
    before = customer["updated_at"]
    resp = client.patch(f"/customers/{customer['id']}", json={"name": "Renamed"})
    assert resp.json()["updated_at"] > before
```

An API test that exists to protect a *warehouse* model. It's in the commerce API
suite with a comment saying why, so whoever breaks it can find out what it was
for.

> **When a model depends on an assumption about another system, test the
> assumption in that other system.** A comment saying "we assume X" is not a
> control. A failing test is.

## The bug: 22% of orders silently orphaned

After building `dim_customer`, 4,550 of 20,247 orders had a **NULL**
`customer_key`.

Row counts reconciled perfectly. `assert_fct_orders_rowcount_matches_staging`
was green. Revenue by country was missing a fifth of the business.

### The cause

`dbt_valid_from` on a snapshot's **first** version is the moment the snapshot
first *ran* — not when the customer came into existence.

The entire 18-month backfill predates the first snapshot run. So every historical
customer's version 1 was valid from *this morning*, and every order they placed
before that fell outside all versions. The range join matched nothing.

```
customer created:  2025-03-14      (in the backfill)
version 1 valid_from: 2026-08-08   (when the snapshot first ran)

order placed:      2025-11-12      ← before valid_from. No match. NULL.
```

### Why it's worse than an error

A range join that matches nothing **fails quietly**. The row stays in the fact
table — hence the clean row count — and simply disappears from anything grouping
by `customer_key`.

Two checks that should agree don't, and neither looks obviously wrong.

### The fix

Back-date the first version to the customer's own `created_at`:

```sql
case
    when row_number() over (
            partition by customer_id order by dbt_valid_from
         ) = 1
    then least(dbt_valid_from, created_at)
    else dbt_valid_from
end as valid_from
```

A customer cannot have placed an order before they existed, so `created_at` is
exactly the right lower bound — not an approximation.

### The residual 99

After the fix, orphans went from 4,550 to **99**. Not zero.

Those 99 were orders placed a few hours *before* their customer's `created_at`.
Which is nonsense — and it was a bug in the **data generator**: customer
eligibility was indexed by signup *date*, but orders got a random *hour* of that
day. A customer who signed up at 18:00 was eligible for an order at 09:00 the
same morning.

Worth noting: the warehouse test caught a bug in the *source*, without knowing
which side it came from. That's the argument for asserting business rules in the
warehouse even when the application also enforces them.

## Using the dimension correctly

The trap, stated plainly:

> **Joining a fact to an SCD2 dimension on the natural key alone MULTIPLIES the
> fact by the number of versions.**

A customer with three versions makes every one of their orders appear three
times. Revenue triples for exactly the customers who changed something.

Two correct joins:

```sql
-- as-of: for historical attribution
on  f.customer_id = d.customer_id
and f.placed_at_utc >= d.valid_from
and f.placed_at_utc <  d.valid_to_or_infinity

-- current: for "who is this customer NOW"
on f.customer_id = d.customer_id and d.is_current
```

`fct_orders` resolves the as-of key **once**, so downstream consumers join on
`customer_key` alone and get the historically correct version without needing to
know any of this. That's the point of doing it in the fact table — you solve it
once instead of hoping every analyst gets it right.

## `valid_to_or_infinity`

```sql
coalesce(dbt_valid_to, cast('9999-12-31 23:59:59' as timestamp)) as valid_to_or_infinity
```

**Why:** so the `BETWEEN`-style join works without a `coalesce` at every call
site. A forgotten coalesce silently drops every fact falling in a row's *current*
version — which is most of your recent data, and it looks like a data lag rather
than a bug.

## The tests

```sql
-- assert_scd2_no_overlapping_versions.sql
where next_valid_from is not null
  and next_valid_from != valid_to_or_infinity
```

Catches **both** failure directions, and they're different bugs:

- **overlap** — the as-of join matches two versions, fans the fact out, revenue
  doubles
- **gap** — matches none, `customer_key` is null, revenue silently disappears

The gap is more dangerous precisely because the row count doesn't change.

```sql
-- assert_scd2_exactly_one_current_per_customer.sql
having count(*) filter (where is_current) != 1
```

Also both directions. **Zero** current versions is the one a naive test misses —
counting rows `where is_current` and checking for duplicates only ever finds the
"two" case.

## What breaks without SCD2

- Historical revenue by country silently restates whenever anyone relocates.
- The same report run twice returns different numbers with no explanation.
- You cannot answer "what was true in March?" for any customer attribute.
- Cohort analysis on customer attributes is meaningless — everyone looks like
  they were always in their current state.

## Try it

```bash
cd transform && dbt build --select dim_customer
```

Then find a customer who relocated:

```sql
select customer_id, country_code, valid_from, valid_to, is_current
from marts.dim_customer
where has_relocated
order by customer_id, valid_from;
```

Multiple rows per customer, non-overlapping windows, exactly one current.
